## 当前实现目标

复用已板测的LCD1+B32位流、FPG1/FWD1与日志报告；补齐统一运行入口、异步实时屏幕、显式任务状态接收、启动/退出回退及可验证运行包。完成后以本机端到端测试为代码验收，新增Python运行链路的实体板/目标Linux验收单列为待测。

### 最小设计检查

1. 结构：屏幕读取同一服务的事件与PL快照，消除画面与当次运行脱节；渲染只拥有LCD写入，guard写入仍只有UDP服务。
2. 使用负担：新增运行入口只要求允许的PC地址、数据来源标签与新日志目录；位流、尺寸、画面页号由工程/硬件确定。
3. 可确定项：动作检查结果、超时和计数来自PL/日志；任务阶段只能由HOST/OPERATOR明确声明，不能由tick推算。
4. 规模：不改已验证RTL，不增加摄像头、模型、图形服务器或新的网络端口；状态帧使用同一UDP9009。
5. 范围：服务当前7020/4384屏幕及已有检查协议；无其它板型/显示后端的自动兼容路径。

最小变更是提取既有UDP循环供原headless入口与新runtime入口共用，并让日志对象接收PL快照。屏幕独立线程以2Hz目标更新，UDP路径不做Pillow绘制或整帧写入。相比另写第二套UDP接收器，这样保持同一协议校验、喂狗规则和会话语义。

日志新增watchdog_sample回调：headless日志不将50ms采样全部写SD；运行日志将快照交给屏幕。其默认空实现用于保留既有无屏服务，不是失败时的备用后端。

runtime按一次FWD1会话运行，END后结束并回退；headless调试入口保留端口以验证END后的拒包。该差异来自两个入口的用途，不提供切换后端的配置。运行状态从已经收到的会话状态推导，不另维护一套结束标志。

所有维护中的Overlay下载入口使用同一协作进程锁；Linux使用标准fcntl，Windows开发/软件夹具使用标准msvcrt。锁一直保持到回退完成，避免同一工程两个进程同时重新配置PL。

## 新任务状态通道

同一UDP端口识别FUI1，头部为`<4sBBHIIQ`，后接UTF-8 JSON和CRC32。op=1请求、129响应；版本1；JSON不超过256字节，且只允许phase/activity/origin三个字段。

- phase：UNKNOWN、WAITING、GRASPING、GRASPED、FOLD_1、FOLD_2、COMPLETE。
- activity：IDLE、THINKING、EXECUTING、PAUSED、ERROR。
- origin：HOST、OPERATOR。

三项均为发送方声明，回包只确认PS接受状态。FUI1不运行PL动作检查、不写COMMIT、不暂停/恢复watchdog。THINKING文字不能替代生产方正确选择ON_RESULT或显式PAUSE。身份/序号/tick独立于FPG1/FWD1；一个任务发布会话对应一次服务运行，换发布会话需重启服务。

source标签必须由操作者声明，因为既有动作协议不能证明数据来自合成、回放或机器人。界面始终标SHADOW，真实任务阶段也标明HOST/OPERATOR来源；无逐通道掩码时仍为灰色。

## 实现前故障清单

- FUI1：长度、版本、CRC、JSON格式/重复键、未知字段、非法枚举、过期序号/tick、不同来源/会话、伪造回包。
- 观察隔离：状态声明不能喂狗；PERIODIC静默仍超时，ON_RESULT思考静默不引入周期门限。
- 并发：帧写入不能阻塞UDP；日志和屏幕状态快照一致；显示异常须退出服务并记录原因。
- 生命周期：SIGINT/SIGTERM、端口占用、显示异常时都停用watchdog；先停止显示线程再重新配置PL，随后恢复B32。
- 输出：不覆盖旧运行目录；LIVE/REPLAY及来源清晰；PS/PL计数分开；最新PNG与逐帧时延可导出，不能称为屏幕照片。
- 交付：LF校验清单、正确资源路径、Python3.8语法、解包导入/测试和位流身份校验。
